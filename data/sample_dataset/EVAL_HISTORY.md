## Reading this table

- **Clear-case accuracy** is the headline number — it's what "no regression" means from one row to the next: it should never go down. **The 2026-08-03 Archive/No-Action row is the first drop (100%→98%)** — reported as-observed, not re-run-until-passing. Traced to confirmed LLM sampling non-determinism at the decision layer (reproduced independently: the identical query passed on a separate re-run), not a retrieval defect or a new code bug — see that report's §2. This broadens, rather than contradicts, the already-documented `qwen3:4b` non-determinism limitation.
- **Hard cases** are tracked for information, not correctness — a hard-case failure isn't necessarily bad (see the 2026-08-03 rows: none of the three hard-case failures so far was a pipeline defect — two were correct refusals to guess under genuine ambiguity, one exposed a ground-truth-construction gap more than a pipeline gap; all are explained in their reports). Conversely, a hard case passing isn't automatically a strong result either — see the Broken Thread Headers report's §2 for a case that passed but at lower rigor than intended (subject-line matching did more work than the stripped-body content the case meant to isolate).
- If clear-case accuracy or Recall@20/@3 ever drops between two rows, treat it as a real regression and investigate before adding further cases — trace actual pipeline output (per the `candidate_index` bug precedent), don't guess at a cause. A drop traced to confirmed LLM non-determinism (as here) is reported honestly rather than hidden by re-running until it passes, but is not treated the same as a code-level regression.
- **Starting with the 2026-08-03 corpus-audit row, this table also tracks corpus changes, not just query additions** — see `CORPUS_COVERAGE_AUDIT.md` and `CORPUS_EXPANSION_ROADMAP.md`. Any row that changed `seed_data.py` requires the full-re-run regression check described in the roadmap; this table is where that check's result gets recorded.
- Non-determinism on the `info_ambiguous_archive_boundary`/`thankyou_ambiguous_lowcontent`-style hard cases has now been observed to vary at the **reranker** level, not just the LLM decision layer, on near-zero-content queries with multiple similar candidates — three separate observations of `info_ambiguous_archive_boundary` produced three different answers. Treat any single run of this query *shape* as one noisy sample, not a stable measurement.
- **2026-08-04: `NOISE_FLOOR_FINDINGS.md`** quantifies this for the first time via `scripts/run_eval.py --repeat N --keys ...` instead of relying on single observations. Key results: `info_ambiguous_archive_boundary` is correct only 1/8 times across all observations to date (confidently wrong 4/8 times, not just "sometimes noisy"); `archive_ambiguous_lakeside`'s previously-reported "honest decline" behavior turned out to be the minority outcome (4/6 combined observations actually confidently attach correctly) — see that report's append-note; `archive_c4_claims_selfresolved` is now 7/8 across all observations (meaningfully stabilized by Stage 1, not fully fixed); `thankyou_ambiguous_lowcontent` is a genuinely stable 6/6 identical decline; a 5-query stratified clear-case sample showed zero instability (15/15 identical answers). Read that document before treating any single-run hard-case result as a stable characterization.
